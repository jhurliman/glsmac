## What normal open actually publishes

`4490b0(request,1)` still chooses the first inactive owner slot through the
existing browse contract. The selected ID remains that **inactive slot**.
A recommendation constructor returning intrinsic Scout ID 2 does not select
ID 2 in the UI. Its return is consumed by the controller, while the tuple is
published through recommendation globals.

The selector obtains the best available reactor and provisional strongest land
components, clears the draft name, sets `9498e0=1` and `9498c8=-1`, then calls
`597de0(owner)`. In the admitted profiles, at least one proposal always
publishes a tuple, so provisional components are replaced.

The controller refreshes Faction capabilities through `577140` and resets
first-new-design global `6aea7c` to -1. The independent reference reuses the
checked capability refresh and matches **every Faction byte** after opening.
It derives meaningful accepted proposals from installed component definitions;
it does not consume native proposals, final tuples or generated names as inputs.

## Recommendation acceptance: 597390 modes

The distinction between an existing match and a hypothetical new record is
what selects the eventual draft:

| State | Native behavior |
| --- | --- |
| Mode 1, filter -1 | Initial recommendation search; category is unrestricted |
| Existing admitted match while mode <=2 | Publish its proposal tuple and reactor to globals; set mode 2; category filter remains -1 |
| No matching record, allocation candidate available, mode <=2 | Publish proposed tuple, reactor and category; set filter to that category and mode 3; return -1 without building |
| Mode 3 | Subsequent calls do not replace published tuple; differing category fails the filter immediately |

Existing matches therefore stay replaceable, while the first genuinely new
proposal locks the output. **Last admitted alias wins until the first new
proposal**, rather than first alias wins or strongest proposal wins.

In recommendation mode the constructor skips the ordinary mode-zero
retirement-history blocker (`5973c3..59741d`). Do not feed the human history
recreation rejection into this draft search. No draft-mode record is allocated,
built, named or activated. General matching can clear an existing match's owner
exclusion bit; this reference requires those bits already clear. Other matching
semantics remain the existing constructor/registry contracts.

The reference reduces equivalent early alias/upgrader proposals to their final
effect. It does not promise the original controller's complete intermediate
request sequence. Native traces retain that sequence separately for provenance.

## First defensive proposal and the advanced distinction

The defensive family begins at `59855c` and submits category 2 at `598826`.
Its relevant selectors differ from the provisional strongest-component loops:

- `595910(owner,land,minimumSpeed=1)` prefers a chassis whose speed is exactly
  1: score 2, versus score 1 for faster chassis. Only a strictly better score
  replaces the choice, so earlier IDs win score ties. The installed result is
  Infantry even when Hovertank is known.
- Armor scans known nonnegative strengths with cost <=99, maximizing twice
  strength. Equal score replaces the prior choice, so later armor IDs win ties.
- The advanced case admits Comm Jammer, bit 9 (`0200`), at `5985cf..598605`.
  It takes precedence over fallback defensive ability choices. None of the
  admitted natural starting grants admits those fallback abilities; their
  masks remain zero. This reference does not generalize those AI/personality
  fallbacks to arbitrary technology states.

Weapon helper `5959c0(owner,budget,0)` chooses the strongest known combat
weapon whose **component cost** does not exceed budget, excluding power >=99
and Conventional Payload ID 20. Equal doubled power chooses the later ID.
The defensive caller starts with budget 1 and considers budget 2,3,...:

1. Stop if the new budget returns the same weapon as the current choice.
2. Otherwise compare complete raw design costs at the selected chassis,
   armor, reactor and ability mask through `5bd1e0`.
3. Accept the weapon and continue only when the new design cost is no greater.

The independent reference uses the existing checked component-cost arithmetic.
In the all-technology control, Hand Weapons and Laser both yield raw cost **6**
with the selected Stasis armor, Singularity reactor and Comm Jammer. Budget 2
therefore accepts Laser. Budget 3 selects Laser again and terminates; it does
not continue to budget 4 and beyond. This explains the final Laser instead of
the provisional Singularity weapon. That first defensive tuple has no active
match, so mode 3 locks it before the other sixteen proposals.

## Why marked startup and missing aliases differ

With normal marked startup records, Morgan's defensive Synthmetal tuple matches
its existing design 256. It stays mode 2. The later offensive proposal also
matches that record, then the category-10 Scout proposal matches intrinsic 2
and replaces the draft with basic Infantry.

Sparta's later fast-land proposals match its existing Speeder recon 320, so
its final tuple is the Rover variant. The other natural profiles finish with
basic Infantry. Existing upgrade/alias proposals do not allocate anything.

If Morgan's first defender has been deactivated, the same defensive Synthmetal
proposal has no active match. It becomes mode 3/category 2; later category 3
and 10 proposals cannot replace it. The extra native control verifies this
against the same caller state and technology, without rerunning the other eight.
The reference derives this distinction by checking the active registry, not
by branching on faction name or a captured final tuple.
