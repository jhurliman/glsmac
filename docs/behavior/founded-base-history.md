# Ordinary founded Base history

**Ordinary creation sets former owner equal to the founding/current owner, and assimilation to0.** It does not initialize former owner to0 or absence. Two actual creation-entry prefixes replace positive former-owner6/assimilation87 canaries with owner1/former1/assimilation0, at global turn0 and9; a peer Base’s distinct history remains unchanged. These execute the actual unconditional creation stores, before later naming/resources/completion, not full founding returns.

Turn9 here means a newly created Base later in play, not reinitialization of an existing Base or a per-faction reset. The source stores use the supplied founding owner without a global-turn gate. The subsequent turn-dependent production-credit logic does not select these initial history bytes. Capture/restart/history migration are separate producers.

Three ordinary file-body save/load pairs retain owner/former/assimilation exactly: [1,1,0], [1,6,0], [1,2,87]. Values are poisoned between write/read and restored with no random calls. Those inputs are declared storage canaries, not proof of how a captured/stale history arose. Load does not normalize a zero-counter former owner to current owner. Existing assimilation upkeep also skips the history update when its incoming counter is already0.

For the riot recipient selector, a newly founded Base therefore carries the positive former owner equal to its current owner. Preserve that exact input and the selector’s existing branch/order; do not replace it with absent/zero to force geographic search. Legacy absent history stays an explicit fidelity boundary until an independent migration policy is chosen.
