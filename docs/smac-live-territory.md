# Saved territory inputs and live Base transactions

Territory rebuilding now consumes one frozen border rule, actual current map
topology, and the Base manager's explicit record sequence. It updates claims
when a complete canonical Base is registered or removed while worker knowledge
is present. Exploration, visibility, remembered improvements, diplomatic inputs
and unit observations are copied unchanged.

`SmacTerritoryRules` owns signed32 RULES row48 and derives the original0..100
clamp. Installed alpha supplies8. This row identity and clamp are established by
the retained original rule-loader disassembly at59c8a3..59c8ba
(`tmp/reference/linear-0059c2e0.json`). Text admission uses the port's existing
strict70-row decimal policy; it does not claim original token-prefix behavior.
Global13 appends the bounded28-byte profile and compares raw values when frozen,
including distinct source values with the same clamped result. World25 compares
the same profile before body decoding. Border0 deliberately leaves every tile
unclaimed, including Base centers, because the cutoff is strict.

`GlsmacTerritoryTopology` builds from each actual Tile's displayed sea predicate.
It follows REGION-FRESH-001's interior parity scan, eight-neighbor component
traversal, no expansion from polar tiles, and final polar IDs63/127. It owns the
result and validates saved regions against current terrain. Land IDs1..61 and
sea65..125 are supported; capacity merging is explicitly rejected before
publication. This does not implement Freshwater markers, original count-table
history, or claim that GLSMAC elevation generation equals the original game's
geography.

The topology is created when `PublishSmacWorkerKnowledge` binds an explicitly
supplied knowledge value to the current world. It is not frozen prematurely at
map generation, while startup may still change terrain. Subsequent unsupported
terrain mutations retain the existing knowledge fence. World25 stores the
optional topology after worker knowledge and before map bytes, with a65,552-byte
maximum checked before copying. Knowledge requires topology; raw map loads do
not infer it. Restoration validates and retains the saved value without
replaying founding or rebuilding saved claims.

BM9 serializes Bases in the explicit manager registration sequence. Removal
erases that record, and later registration appends. This is the original
algorithm's ordered input expressed in port identities, not a claim that port
IDs encode age or original record slots. Restore preserves that sequence; it
does not sort by ID. Equal-distance claims therefore retain the later-record
rule across save and restore.

Live construction checks a complete canonical context and allocation before
claiming a center or advancing IDs. Spawn stages the complete claim replacement
before registration; removal stages before membership changes and retains the
existing prohibition on deleting a conventional home Base. The claim swap
precedes the existing spawn/despawn callback. A private pending-center exception
exists only for the candidate already constructed for native SpawnBase; it
cannot hide a different unregistered Base. Snapshot construction remains a
private decoded-record path, and pending restored knowledge stays unavailable
until both manager registries drain.

This is an actual native complete-record creation/removal path. It does not
invent an allocation for the generic GSE `spawn_base` call or activate a new
default founding routine. Incomplete creation remains rejected when knowledge
is active. Capture, terrain editing with knowledge, region-capacity merging and
full first-worker founding policy remain separate callers.
