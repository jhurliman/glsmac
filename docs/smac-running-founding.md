# Running Colony founding

The local `found_base` event now consumes an actual ready Colony Pod and publishes a second or later canonical Base. The frontend B key queues that event using the selected Unit ID. Native admission is rechecked at dispatch; it does not expose arbitrary script events through the knowledge fence.

The current path is an ordinary generated, non-scenario, local human campaign at original difficulty 3 with the saved no-project capability. It requires an existing same-owner Base, an actionable land Colony Pod, an empty non-rocky site without fungus or a Monolith, no adjacent Base, and own or unclaimed raw territory. Foreign-territory diplomatic choices, first-owner late founding, sea founding, capacity-failure behavior, naming dialogs and the unused successful-founding-turn stamp are not implemented here. The existing port Base-name producer supplies the name. These limits are explicit admission boundaries, not original universal rules.

## Inputs and transaction

The producer uses the owned catalog and saved custom designs for the later-turn production scan: enabled prerequisite/triad/exclusion checks, prototyped custom designs, signed armor score, plan multiplier, nonland division and unsigned cost, with later equal scores winning. Scout 2 remains the original fallback. Initial minerals use **retained SUPPORT** and the frozen retool exemption, independently of current SUPPORT used by ordinary upkeep. Current and baseline target/minerals agree; the queue is explicitly empty.

The new Base starts at population one, receives actual faction facility grants without a first-Base HQ grant, and uses registered positional Pop roles. A private candidate runs the existing automatic allocator against actual tiles, orbital counters, staged territory, current social/resource inputs and existing assignments. Fresh packed specialist storage is explicitly zeroed as a port allocation policy. Food remains zero or the measured initial deficit marker; founding does not post a turn of income.

All registry, assignment, update-queue, territory and Unit-removal storage is prepared before the authority changes. Base registration, center/ID publication, Unit removal and knowledge swaps have no intervening callbacks. Hooks run afterward. The consumed Pod observation is removed; exploration, remembered improvements and observer relationships are retained exactly. No startup reveal is replayed.

The prepared Unit-removal seam also accepts an optional prepared newborn and an ordered removal batch. It stages from that candidate registry/roster/sight, preserves survivor order, cancels an unpublished newborn spawn and owns retired wrappers through notification exceptions. Callers commit the prepared creation first and omit its spawn notification if the removal contains its ID. This is used here for a single Pod and separately tested with an existing Unit plus a newborn; it does not itself implement mineral-shortage selection.

Frontend despawn clears selected and previously deselected pointers even when an exhausted Unit is absent from the selectable vector. It removes tile membership before choosing the next selection.

A cached incremental build and ten tracked native groups pass: manufactured Pod -> real movement events -> real founding event -> complete snapshot restoration; atomic terrain/claim/late-role rejection; saved custom-design tie and retained-credit cases; composed existing/newborn removal and abandonment; the three prior Colony cases; and three actual frontend preview/despawn lifetime cases. The latter use synthetic badge/selection assets with the actual frontend dispatch and selection path. Eight changed production translation units pass targeted C++ analysis. No full platform or rendered interactive-game claim is made.
